# RCMap 1.1 — RollingCube 关卡地图描述语言

**状态**：Designed

**版本**：1.1

**日期**：2026-07-30

**适用范围**：第一章及后续所有关卡 GDD

---

## 1. 设计目标

RCMap 用于在 GDD 中准确描述：

- 地形位置与类型；
- 地形高度；
- 同一 XZ 坐标上的多层结构；
- 玩家出生点与关卡终点；
- 机关、箱子、移动平台等实体；
- 下落路径和跨层落点；
- 标准解路线与最终符文朝向。

RCMap 描述的是关卡设计空间，不直接使用 Unity GameObject 的中心坐标。

---

## 2. 核心规则

1. 地图必须写在等宽代码块中。
2. 地图内部只允许 ASCII 字符，不使用中文名称或全角符号。
3. 每个格子的宽度固定为四个字符，例如 `[#S]`。
4. 不使用 `—`、`|` 等连接线表达道路连接。
5. 两个格子是否相邻，完全由 XZ 坐标决定。
6. Y 表示该格的“可站立表面高度”，不是地形物体中心或玩家中心。
7. 所有高度必须是 `0.25` 的整数倍。
8. 多层结构必须分别写在不同的 `@layer` 中。
9. 机关在地图中使用单字符别名，完整含义写在 `@entity` 声明中。
10. 地图描述几何关系，不自动保证路线可通行；可通行性由移动规则、机关状态和标准解共同验证。

---

## 3. 坐标系与方向

```rcmap
+x = map right
-x = map left
+z = map up
-z = map down
+y = walkable surface altitude

R = +x
L = -x
U = +z
D = -z
```

`R`、`L`、`U`、`D` 始终表示地图方向，与摄像机方向和立方体当前朝向无关。

玩家中心高度由系统推导：

```text
player_center_y = surface_y + cubeHalfSize
```

例如，RCMap 中地面写作 `y=+0.00`，且 `cubeHalfSize=0.5` 时，玩家中心位于
`y=+0.50`。

当前立方体没有需要单独描述的“正面”，因此 RCMap 不定义 `facing`。出生状态只记录
符文面的世界方向。

---

## 4. 固定宽度格子

每个格子使用以下格式：

```text
[BO]
```

- `B`：Base，地形或支撑类型；
- `O`：Object，该格上的对象或标记。

### 4.1 Base 字符

| 字符 | 含义 |
|------|------|
| `.` | 空间，没有支撑 |
| `#` | 普通静态地形 |
| `=` | 动态地形，如电梯、移动平台或升降桥 |
| `~` | 易碎地形 |
| `X` | 在该层不可穿越的实体或墙体 |

### 4.2 Object 字符

| 字符 | 含义 |
|------|------|
| `.` | 没有额外对象 |
| `S` | 玩家出生点 Start |
| `E` | 关卡终点 End |
| `a-z` | 机关或实体别名 |
| `0-9` | 额外实体别名 |
| `*` | 同一格存在多个对象，详情由 `@place` 声明 |

大写 `S` 和 `E` 是保留字符，不能作为普通实体别名。

### 4.3 常见组合

| 格子 | 含义 |
|------|------|
| `[..]` | 完全为空 |
| `[#.]` | 普通静态地形 |
| `[#S]` | 普通地形上的出生点 |
| `[#E]` | 普通地形上的终点 |
| `[#a]` | 普通地形上的机关 `a` |
| `[=b]` | 动态平台 `b` |
| `[~c]` | 易碎地形 `c` |
| `[#*]` | 普通地形上有多个对象 |

同一个机关占据多个格子时，可以在多个格子中重复使用同一个别名。

---

## 5. 图层语法

每个高度单独定义一个图层：

```rcmap
@layer y=+0.00
      x+00 x+01 x+02 x+03
z+01 [..] [#.] [#.] [..]
z+00 [#S] [#.] [#a] [#E]
z-01 [..] [..] [..] [..]
```

图层遵循以下规则：

- X 坐标从左到右递增；
- Z 坐标向地图上方递增；
- 文本中较大的 Z 写在较上方的行；
- 所有行必须拥有相同数量的格子；
- 对角相邻不代表可以移动；
- 同高度、上下左右相邻的可行走格默认双向连通；
- 空格 `[..]` 仍必须保留，不能通过省略单元格改变列对齐。

坐标默认使用带符号的两位整数，例如 `x-05`、`x+00`、`z+01`。如果关卡超出
`-99` 到 `+99`，整张地图必须统一扩大坐标字段宽度，不能只扩大个别列。

---

## 6. 实体和机关声明

地图只显示单字符别名，详细信息写在地图之后：

```rcmap
@entity a
type=ElevatorSwitch
name=bridge_switch
at=(x=+02,z=+00,y=+0.00)
targets=[b]
activator=player_or_box
hold=1.0s

@entity b
type=Elevator
name=bridge
at=(x=+03,z=+00,y=+0.00)
target=(x=+03,z=+00,y=+1.00)
reset=true
```

坐标必须使用带字段名的形式：

```text
(x=...,z=...,y=...)
```

禁止使用没有字段名的 `(2,0,1)`，避免混淆 XYZ 顺序。

实体 `type` 应优先使用项目中的正式机制名，例如：

- `PushableBlock`
- `Elevator`
- `ElevatorSwitch`
- `FragileGround`
- `Conveyor`
- `RisingTerrain`
- `SceneSwitcher`

`name` 使用稳定、唯一的 ASCII `snake_case` 名称，供正文、标准解和验收标准引用。

## 7. 出生点与终点

### 7.1 出生点

`S` 表示玩家出生点。出生声明至少记录位置和初始符文方向：

```rcmap
@start S
at=(x=+00,z=+00,y=+0.00)
rune=UP
```

当前玩法只需追踪符文面的六种世界方向：

```text
UP
DOWN
LEFT
RIGHT
FORWARD
BACK
```

只要立方体仍然只有一个需要识别的特殊符文面，就不需要描述完整的 24 种立方体旋转
状态。如果未来多个面拥有不同符文，再扩展完整朝向语法。

### 7.2 终点

`E` 固定表示带有 `SceneSwitcher` 的关卡终点，并默认包含以下不可覆盖的核心规则：

```text
require = rune.DOWN
dwell = 2.0s
```

因此关卡 GDD 不重复书写 `require=rune.DOWN` 或 `dwell=2.0s`。

地图已经唯一标出 `E` 的位置时，终点声明只需记录下一场景：

```rcmap
@end E
next=Chapter1_Scene2
```

如果正文需要脱离地图单独引用终点坐标，可以显式重复位置：

```rcmap
@end E
at=(x=+03,z=+00,y=+0.00)
next=Chapter1_Scene2
```

显式坐标必须与地图中的 `E` 一致。

若未来确实需要不同的停留时间，必须先修改全局符文终点规则和 RCMap 版本，不能由某一
关卡静默覆盖。`require=rune.DOWN` 在 RCMap 1.1 中始终不能覆盖。

## 8. 高低落差

一维路径可以附加剖面图，快速表达高度：

```rcmap
@section z=+00

x      | x+00  | x+01  | x+02  | x+03
top_y  | +0.00 | +0.00 | +0.50 | +1.00
cell   | #S    | #.    | #.    | #E
```

这等价于简略表达：

```text
[0] - [0] - [0.5] - [1]
```

但每一列固定宽度，不会因为文字长度产生错位。

`@section` 是辅助剖面，完整三维结构仍以 `@layer` 为唯一权威来源。如果剖面与图层
冲突，以图层为准，并将冲突视为文档缺陷。

地图能够描述向上的阶梯，不代表玩家当前一定可以通过。由于第一章不启用攀爬，从低处
直接向高处移动应被判定为阻挡，除非存在电梯、升降地形或其他明确机制。

---

## 9. 多层结构

同一个 XZ 坐标可以在多个高度拥有地形：

```rcmap
@layer y=+2.00
      x+00 x+01 x+02
z+00 [#S] [#.] [..]

@layer y=+0.00
      x+00 x+01 x+02
z+00 [#.] [#.] [#E]
```

这里：

- 高层位于 `y=+2.00`；
- 低层位于 `y=+0.00`；
- 高层的 `(x=+02,z=+00)` 是空格；
- 玩家从高层边缘滚出后，可能被低层的终点格接住。

所有设计上有意义的玩家或箱子下落都必须显式声明：

```rcmap
@drop d1
actor=player
from=(x=+01,z=+00,y=+2.00)
dir=R
land=(x=+02,z=+00,y=+0.00)
```

`actor` 使用 `player` 或已经声明的实体别名。省略时默认为 `player`。`from` 是触发
下落动作前 actor 所在的格位，`dir` 是进入无支撑列的方向，`land` 是最终落点。

`land` 表示目标 XZ 列中最先接住玩家的可站立表面。即使可以从图层推断，也必须声明，
以便验证：

- 落点高度；
- 落点是否有安全空间；
- 是否存在更高的意外拦截层；
- 落地后的符文朝向是否需要重新观察；
- 反方向是否因攀爬禁用而不可通行。

---

## 10. 同一格的多个对象

如果玩家出生在机关或移动平台上，地图使用 `*`：

```rcmap
@layer y=+0.00
      x+00
z+00 [=*]

@place
at=(x=+00,z=+00,y=+0.00)
contains=[S,a]
```

随后必须分别声明 `S` 和 `a`。

所有使用 `*` 的格子都必须有且仅有一个坐标匹配的 `@place` 声明。

## 11. 标准解

每关至少定义一个标准解：

```rcmap
@solution primary
route="R PUSH(a,R) DROP(d1) U RIDE(b) R WAIT(2.0s)"
steps=4
start_rune=UP
end_rune=DOWN
end_at=E
```

标准解语法：

- `R`、`L`、`U`、`D` 表示一次成功的正常滚动；
- `PUSH(a,R)` 表示玩家向 `R` 滚动一格，同时将箱子 `a` 向 `R` 推动一格；
- `RIDE(b)` 表示实体 `b` 接管并移动玩家；不计步数，也不改变符文朝向；
- `DROP(d1)` 表示执行已经声明的下落 `d1`；它是结果事件，不重复计算触发该下落的
  滚动或推动步数；
- `WAIT(n)` 表示停留 `n` 秒，不计入步数；
- `steps` 统计普通滚动和 `PUSH`；不统计 `RIDE`、`DROP` 或 `WAIT`；
- `start_rune` 必须与 `@start` 一致；
- `end_rune` 必须为 `DOWN`；
- `end_at` 必须为 `E`。

动作参数中的方向仍使用地图方向。所有动作必须引用已经声明的实体或下落：

```text
PUSH(entity_alias,direction)
RIDE(entity_alias)
DROP(drop_id)
WAIT(seconds)
```

`RIDE` 后玩家位置变为该实体声明的 `target`，除非实体另有明确的 rider 落点声明。
`DROP` 必须紧跟在造成失去支撑的滚动或 `PUSH` 之后。物理下落可能需要 Play Mode
确认；静态解法只能把经过重复验证的稳定落点和朝向结果作为后续步骤前提。

涉及机关时，可以增加状态断言：

```rcmap
assert=[bridge.raised,box_a.on_switch,rune.DOWN]
```

标准解必须同时验证：

1. 每一步位置合法；
2. 所有机关处于预期状态；
3. 玩家没有依赖未声明的攀爬；
4. 所有下落对应已声明的 `@drop`；
5. 最终位置为 `E`；
6. 最终符文面朝下；
7. `WAIT(2.0s)` 后满足全局终点条件。

若存在合理的多解，应依次声明：

```text
@solution primary
@solution alternate_1
@solution alternate_2
```

若存在绕过本关核心教学目标的更短路线，应记录为设计漏洞，而不是合法备选解。

## 12. Level 01 示例

按照第一关当前 GDD 的预期结构，地图可以表达为：

```rcmap
@level Chapter1_Scene1
@grid cell=1.00 height_step=0.25

@layer y=+0.00
      x-05 x-04 x-03 x-02 x-01 x+00 x+01
z+01 [..] [..] [..] [..] [#.] [#.] [#.]
z+00 [#S] [#.] [#.] [#.] [#.] [#E] [#.]
z-01 [..] [..] [..] [..] [#.] [#.] [#.]

@start S
at=(x=-05,z=+00,y=+0.00)
rune=UP

@end E
next=Chapter1_Scene2

@solution primary
route="R R R R R R U L D WAIT(2.0s)"
steps=9
start_rune=UP
end_rune=DOWN
end_at=E
```

这个表示不需要在地图中写“出生”“调整点”“终点”等长文字：

- `S` 明确表示出生点；
- `E` 明确表示终点；
- `3 × 3` 草地平台由坐标和地块位置直接表达；
- `E` 位于草地平台中央；
- 调整路线中的普通格不需要拥有会破坏对齐的长标签；
- 正文讨论某一调整格时，直接引用其坐标。

## 13. 完整性与验证规则

一份有效的 RCMap 必须满足：

1. 每个地图格严格使用 `[BO]` 格式。
2. 地图代码块内不出现中文或全角符号。
3. 每一行格子数量与 X 坐标数量一致。
4. 同一份地图中的坐标字段宽度一致。
5. 所有机关别名都有对应的 `@entity`。
6. `S` 和 `E` 各出现一次，除非未来的 RCMap 版本明确支持多出生点或多终点。
7. `@start` 的坐标和符文方向与地图一致。
8. `@end` 不重复声明 `require=rune.DOWN` 和 `dwell=2.0s`。
9. 所有 Y 值都是 `0.25` 的整数倍。
10. 所有显著下落都有 `@drop` 声明。
11. 动态平台必须声明初始位置和目标位置。
12. 所有 `*` 格子都有对应的 `@place`。
13. 标准解的每一步都落在有效地形或合法机关上。
14. `PUSH`、`RIDE` 和 `DROP` 只引用已经声明的实体或下落。
15. `DROP` 中的 actor、方向和落点与对应推动或滚动一致。
16. 标准解的 `steps` 与普通滚动加 `PUSH` 的总数一致。
17. 标准解结束时必须位于 `E`，并满足 `rune.DOWN`。
18. 标准解不得依赖随机的物理旋转结果。
19. 涉及物理下落时，GDD 必须要求通过多次 Play Mode 测试验证落点。
20. 关卡中如果存在更短的绕过路线，应将其列为合法备选解或设计漏洞。
21. 地图、标准解、机关声明和 GDD 验收标准必须引用同一组坐标与实体别名。
22. `@section` 与 `@layer` 冲突时必须修正文档，不能保留两套不同描述。

## 14. GDD 使用约定

每一份关卡 GDD 的“关卡布局”章节应按以下顺序提供信息：

1. `@level` 和 `@grid`；
2. 从最高到最低排列的全部 `@layer`；
3. 必要的 `@section` 辅助剖面；
4. `@start` 和 `@end`；
5. 所有 `@entity`；
6. 所有 `@place`；
7. 所有 `@drop`；
8. `@solution primary`；
9. 合法备选解或已知设计漏洞。

正文讨论位置时必须引用坐标或实体稳定名称，不再通过“左边那个方块”“终点前的调整点”
等可能产生歧义的自然语言作为唯一定位方式。

RCMap 是关卡空间结构的权威来源。Chapter 1 场景由 `Chapter1SceneBuilder` 按 RCMap
生成；修改地图时必须同步更新对应 GDD、场景生成器和主路线测试。三者不一致时，不得把
该关卡标记为完成。
