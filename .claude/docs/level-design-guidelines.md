# RollingCube 关卡设计与搭建规范

> 面向后续参与关卡设计、RCMap 编写、Unity 场景搭建和路线测试的 Agent。
>
> 在修改 Chapter 1 的任何关卡前，必须先阅读本文、对应的 `level-XX.md`、
> `level-map-schema.md` 和本关使用的机制 GDD。

## 1. 目标

RollingCube 的关卡不能只是“把本关机关放进一个能通关的场景”。一个合格关卡需要同时
满足：

1. 核心机制清楚可读；
2. 空间本身具有可辨认的轮廓、方向变化和探索感；
3. 符文朝向、下落和路线选择形成有意义的思考；
4. 难度符合当前教学阶段，不用无关复杂度干扰本关主题；
5. 自动化路线正确，人工试玩时也具有节奏和表现力。

复杂度不是质量。增加格子、层数或机关数量，只有在它们承担明确职责时才有价值。

## 2. 设计源与强制同步

以下文件共同构成关卡事实来源：

- 章节规则：`design/gdd/chapter-01.md`
- 关卡地图：`design/gdd/level-01.md` 至 `level-09.md`
- 地图语言：`design/gdd/level-map-schema.md`
- 机制规则：`design/gdd/mechanism-*.md`
- 场景生成器：`Assets/Editor/Chapter1SceneBuilder.cs`
- 主路线测试：`Assets/Tests/PlayMode/Chapter1CompletionTests.cs`

修改关卡时，必须同步更新：

1. 对应 `level-XX.md`；
2. `Chapter1SceneBuilder` 中的关卡构建方法；
3. 主路线、备选路线和必要的机制行为测试；
4. 由构建器生成的 Unity 场景。

四者不一致时，不得声称关卡完成。

## 3. 从“机关测试场”转向“完整关卡”

### 3.1 机关测试场的典型特征

- 起点、机关和终点处于同一条直线；
- 两个矩形平台之间用机关连接；
- 玩家站在起点即可看完整条通关路线；
- 地形只负责承载机关，本身不产生观察、选择或朝向规划；
- 玩家触发机关后只需一直按同一个方向；
- 落地即踩中终点，没有最后一次有意识的操作；
- 为了展示新机制而强行把它放进场景，去掉机关后地图没有任何空间特征。

### 3.2 完整关卡应具备的变化

- 路线至少包含一次有意义的转向；
- 机关改变玩家可进入的空间，而不只是播放动画；
- 玩家经历“发现—判断—行动—观察反馈—利用结果”；
- 下落前或进入终点前需要观察符文朝向；
- 分叉具有不同的空间体验，即使两条路线都合法；
- 场景轮廓存在凹凸、留白、高低或前后遮挡，不是一眼读完的长条；
- 失败路线能够解释规则，并允许复位或恢复，不把玩家永久卡住。

## 4. 标准设计流程

### 第一步：写玩家经历

在画地图前，用几句话回答：

- 玩家出生后首先看到什么？
- 核心机关何时被发现？
- 玩家需要产生什么疑问？
- 机关触发后，玩家从哪里观察变化？
- 玩家如何利用刚刚发生的变化？
- 终点前的最后一个判断或操作是什么？

如果这些问题只能回答“往前走、触发、继续往前”，地图通常还没有完成设计。

### 第二步：明确唯一教学主题

每关应有一个主要教学目标，其他内容只负责支撑它。

例如：

- 第二关：多层下落前的符文朝向规划；
- 第三关：发现并使用压力开关与升降桥；
- 后续关卡：推动、搭乘、复位或组合机制。

不要让多个新机制同时争夺注意力。教学关可以有空间选择，但不应让次要谜题压过核心
机制。

### 第三步：先写 RCMap

所有地图提案必须用 RCMap 表达，不得只使用自然语言、临时字符图或“左边的平台”
之类的模糊描述。

RCMap 至少需要包含：

- 全部高度层；
- `S`、`E` 和机关坐标；
- 所有显著下落的 `@drop`；
- 动态平台的初始位置与目标位置；
- 主路线；
- 合法备选路线；
- 起始和结束符文方向；
- 路线步数和必要断言。

向用户讨论地图时也应展示 RCMap，保证坐标、方向和图层是共同语言。

### 第四步：验证路线和符文

在写 Unity 代码前，逐步验证：

- 每次滚动是否落在合法支撑上；
- 上升移动是否被禁用规则阻挡；
- 每个 `DROP` 的来源、方向和落点是否正确；
- 动态机关在对应时刻是否已经到位；
- 路线步数是否准确；
- 抵达 `E` 时是否为 `rune.DOWN`；
- 是否存在更短的意外绕过路线。

不能依赖物理下落后的随机旋转来决定符文方向。

### 第五步：用户批准后再搭建

在修改文件前，向用户展示：

- 完整 RCMap；
- 主路线和备选路线；
- 本关的教学目标；
- 两条路线或下落点的差异；
- 机关动画的时序；
- 计划修改的文件列表。

获得批准后，再更新 GDD、构建器、测试和场景。

### 第六步：自动化和视觉双重验证

自动化检查：

- Unity 编译无错误；
- 主路线通过；
- 每条声明的备选路线通过；
- 关键机关状态和时序有单独测试；
- 场景切换到正确的下一关。

视觉与人工检查：

- 从实际镜头观察空间轮廓；
- 检查高层是否遮挡主要路线；
- 检查开关、桥和终点是否能够被辨认；
- 确认玩家不会在起点一眼看穿全部答案；
- 试玩移动节奏、等待时间和失败恢复；
- 不因测试通过就直接认定“有趣”或“好看”。

## 5. 空间设计原则

### 5.1 转弯必须承担职责

可以承担的职责包括：

- 改变符文朝向；
- 揭示新的空间或机关；
- 让玩家回看刚刚触发的变化；
- 将直达路线改为探索支路；
- 为场景构图制造层次；
- 在终点前提供最后一次调整。

不得为了增加步数而添加没有意义的蛇形道路。

### 5.2 不要把答案排在一条轴线上

默认避免让 `S`、核心机关、桥口和 `E` 全部位于同一条 X 或 Z 轴。

至少考虑以下一种处理：

- 开关位于支路；
- 桥后发生转向；
- 终点位于下层或 L 型末端；
- 通过高差或遮挡分阶段揭示路线；
- 让玩家触发机关后回到先前经过的位置。

### 5.3 使用留白

空格不是浪费。沟壑、缺口和平台之间的距离可以：

- 强化路线轮廓；
- 区分功能区域；
- 让动态桥或移动平台更醒目；
- 避免地图变成一整块无方向感的大平面。

### 5.4 终点不能只是路线的句号

避免：

- 落地立即压中 `E`；
- 直线尽头直接放置 `E`；
- 玩家不需要考虑符文方向即可撞上终点。

更好的方式：

- 落地后再滚动一至数格；
- 将终点放在 L 型或转角末端；
- 在终点周围保留恢复或调整空间；
- 让标准路线自然以 `rune.DOWN` 抵达，而不是依靠偶然。

## 6. 高度与下落设计

### 6.1 每一层必须有明确职责

高度层可以承担：

- 核心解谜路线；
- 不同符文朝向结果；
- 机关启动前后的不同状态；
- 失败或观察路线；
- 纯视觉构图。

如果某一层只用于装饰，应在 GDD 中明确写出 `decoration_only` 的意图，并确保玩家
无法误认为它是必经路线。

不要为了“显得立体”而增加没有玩法或视觉价值的层。

### 6.2 层间默认提供多个可读下落点

当层间转换是关卡思考的一部分时，默认至少设计两个可观察的下落点，除非本关明确是
单路径教学。

两个下落点可以：

- 落到同一点，但产生不同符文方向；
- 落到不同位置，随后汇合；
- 一条较近但落地后需要调整；
- 一条上层绕行较远，但落地后更直接；
- 两条步数相同，仅提供不同空间体验。

不要把第二个下落点简单做成死亡陷阱。错误选择应尽量解释规则、允许恢复，或在 GDD
中明确其教学目的。

### 6.3 下落前应有观察空间

玩家接近边缘时，应有机会看见：

- 可能的落点；
- 落点附近的终点或路线；
- 另一处下落选择；
- 当前符文面可能产生的结果。

避免玩家在看不见任何信息时只能盲跳。

## 7. 机制教学与表现

### 7.1 机关需要完整闭环

第一次教学机关时至少包含：

1. 发现机关；
2. 触发机关；
3. 观察可见变化；
4. 返回或移动到变化区域；
5. 实际利用机关通行。

仅踩下开关并立刻进入终点，不足以构成完整教学。

### 7.2 多对象动画应设计时序

多个桥面、地块或门同时变化时，考虑：

- 哪个对象先动；
- 动画从玩家侧向远端传播，还是反向传播；
- 延迟是完全串行还是重叠级联；
- 玩家是否站在能够看清变化的位置；
- 总等待时间是否拖慢节奏。

第三关的参考做法是：

```text
switch_hold = 1.00s
bridge_west_delay = 0.00s
bridge_east_delay = 0.50s
bridge_move_duration = 1.25s
```

近端桥先动，远端桥稍后跟上，形成向前延伸的视觉效果。

### 7.3 机制复杂度要匹配关卡定位

- 解谜关：不同路线可以产生朝向差异和需要规划的后果；
- 教学关：可以提供选择，但两条路线最好都能解释机制并顺利通关；
- 综合关：可以组合此前已经学会的机制，但一次只增加一个主要新变量。

## 8. 美术与装饰层

装饰元素应强化空间阅读，而不是遮挡玩法。

可以使用：

- 高台、断崖和远景岛形成纵深；
- 花、草、石板、木桩、原木、藤蔓、浮萍和荷花区分区域；
- 植被密度或颜色引导玩家注意开关和桥口；
- 留白、水面或沟壑突出动态机关。

需要避免：

- 装饰物遮住格子边缘或落点；
- 可碰撞装饰制造未记录的阻挡；
- 装饰高台看起来可到达但没有任何用途；
- 终点、开关和普通装饰使用过于接近的视觉权重。

装饰层不应进入标准解，也不应改变自动化测试的路线坐标。

## 9. 推荐的路线结构

以下结构可以作为设计起点，但不是必须套用的公式。

### 解谜型

```text
观察多个边缘
  → 选择下落点
  → 符文方向产生差异
  → 下层路线汇合或分化
  → 最后调整
  → E
```

### 机关教学型

```text
曲折接近
  → 发现支路开关
  → 触发并观察机关
  → 返回主路线
  → 使用机关
  → 轻量分叉
  → E
```

### 表现型机关

```text
玩家停在清楚的观察点
  → 近端对象先变化
  → 状态向远端传播
  → 通路完整形成
  → 玩家立即使用新通路
```

## 10. 常见反模式

发现以下情况时，应停止搭建并返回 RCMap：

- 两个大矩形平台加一条桥；
- 整关只需要连续按同一方向；
- 新机关只是被摆进场景，没有改变路线；
- 所有地形都在同一高度且没有构图理由；
- 增加多层但每层只有一条唯一出口；
- 第二条路线明显更差且没有教学意义；
- 玩家看不到机关变化；
- 动画同时开始、同时结束，缺少方向和节奏；
- 终点位于落点；
- 只写主路线，没有检查意外捷径；
- 只依靠测试结果判断关卡质量。

## 11. 设计提交前检查表

### 玩家体验

- [ ] 能用一句话说清本关唯一的主要教学目标。
- [ ] 玩家经历了发现、判断、行动、反馈和利用。
- [ ] 起点无法一眼展示完整答案。
- [ ] 路线至少有一次有意义的方向变化。
- [ ] 终点前还有一次有意识的操作。

### 空间

- [ ] 地图具有可辨认的整体轮廓。
- [ ] 每个高度层都有明确职责。
- [ ] 层间转换若参与解谜，至少有两个可读下落点或明确的单路径理由。
- [ ] 分叉路线具有不同体验，而不是无意义复制。
- [ ] 装饰层不遮挡、不误导、不参与标准解。

### 符文与终点

- [ ] 每条声明路线的符文方向已逐步验证。
- [ ] 所有标准解最终为 `rune.DOWN`。
- [ ] `E` 不位于自动落点。
- [ ] 错误朝向抵达终点后仍能恢复或调整。

### 机关

- [ ] 机关改变了玩家可进入的空间。
- [ ] 玩家能从合理位置看到机关反馈。
- [ ] 多对象动画具有经过设计的顺序和间隔。
- [ ] 机关等待时间足够清楚但不过长。
- [ ] 失败状态不会造成永久卡死。

### 交付

- [ ] GDD 使用合法 RCMap。
- [ ] GDD、构建器、测试和场景坐标一致。
- [ ] 主路线和所有合法备选路线均有 PlayMode 覆盖。
- [ ] Unity 编译错误为零。
- [ ] 已检查 Unity 场景层级和实际坐标。
- [ ] 已通过截图或 Scene View 检查视觉轮廓。
- [ ] 已提醒用户进行最终手感试玩。

## 12. Agent 交付格式

提出新地图时，按以下顺序向用户展示：

1. 本关主要教学目标；
2. 预计的玩家经历；
3. 完整 RCMap；
4. 主路线与备选路线；
5. 两条路线的差异；
6. 机关动画时序；
7. 已验证的步数与符文结果；
8. 计划修改的文件；
9. 等待用户批准。

搭建完成后，必须报告：

- 修改了哪些文件；
- 场景是否由构建器重新生成；
- Unity 是否编译成功；
- 运行了哪些测试及结果；
- 是否完成视觉检查；
- 是否存在非阻塞警告；
- 是否暂存或提交了文件。

## 13. 最终判断问题

在交付前再次回答：

1. 玩家能否站在起点一眼看完整个答案？
2. 路线上是否存在至少一次有意义的方向变化？
3. 核心机关是否真正改变了玩家可走的空间？
4. 下落或分叉是否提供了观察和判断？
5. 去掉机关后，这张地图是否仍具有可辨认的空间轮廓？

如果多数答案是否定的，这通常仍是机关测试场，而不是完整关卡。
